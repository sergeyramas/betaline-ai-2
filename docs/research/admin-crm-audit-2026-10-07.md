## 0. Коротко

- **У Betaline сейчас нет CRM вообще.** Лиды с custom/custom2/апекса живут только карточками в Telegram-группе. Запись в PocketBase в `api/lead.js` — тихий no-op (переменной `PB_URL` нет ни в одном `.env` на base-vps, домена `pb.betaline-ai.ru` нет в DNS). Sheets и Resend мертвы. Nuxt-CRM на `crm.betaline-ai.ru` (Supabase, Vercel) жива только как страница логина — лиды в неё никто не пишет.
- **Заявка может потеряться молча (нашёл Codex, подтверждено по коду).** `api/lead.js` отвечает `{ok:true}`, если «успешен» хотя бы один канал, а `sendToCRM` без `PB_URL` завершается «успешно» всегда. Значит, если упадёт Telegram — посетитель увидит «заявка принята», цель Метрики `audit_lead` засчитается, а лид не попадёт никуда.
- **Ответить клиенту с сайта нельзя.** Чат-виджет односторонний: оператор видит переписку в Telegram-теме, но его ответ до браузера посетителя не доходит (виджет не опрашивает сервер). Бан/закрытие чата завязаны на мёртвые Google Sheets.
- **В Telegram-боте @BetalineAI_bot ответить можно** — reply на карточку в админ-группе или сообщение в персональной теме лида пересылается клиенту. Но история лежит в SQLite бота, стадий нет, лог «в CRM» пишется в мёртвые Sheets.
- **У Узбекистана (PC Market, «Агата») есть ровно то, чего не хватает:** единая база диалогов в Postgres, инбокс оператора, перехват/возврат бота (`ai_paused`), очередь доставки в Telegram с ретраями, вход по паролю с подписанной cookie, PWA. Но **нет воронки/канбана** и **нет ролей**.
- **Рекомендация:** отдельный сервис `admin.betaline-ai.ru` на base-vps (Node 22 + Fastify + локальный Postgres, который там уже работает; интерфейс — лёгкая vanilla-PWA), портировать из узбекского ядро инбокса (схема, take/release, outbox, auth, sw.js), дописать свою CRM-часть (лид + стадии + канбан). Nuxt+Supabase-CRM не воскрешать.
- **Размер:** полный MVP ≈ 15–20 рабочих дней (после ревью Codex; было 10–14). Урезанный «MVP-0» (все заявки + CRM + канбан + PWA, чат и бот пока в Telegram) ≈ 8–10 дней. Вердикт Codex — «согласен с правками», см. §6.

### 1.2. Два разных бота — важно для архитектуры

- **@betalineForm_bot** — «служебный»: шлёт карточки лидов и темы чата в группу уведомлений, принимает callback-кнопки через вебхук на апексе. Клиенты с ним не общаются.
- **@BetalineAI_bot** — «клиентский»: с ним переписываются люди. Работает через long-polling в `bot.py`, поэтому вебхук на него поставить нельзя без переделки бота (Telegram не даёт одновременно polling и webhook). Отправлять сообщения тем же токеном из другого процесса — можно.

## 4. Архитектура MVP

### 4.1. Развилка по стеку

| Вариант | Плюсы | Минусы |
|---|---|---|
| **A. Свой лёгкий сервис** (Node 22 + `pg` + небольшой HTTP-фреймворк, например Fastify — по замечанию Codex, чтобы не писать роутинг/cookie/лимиты тела руками; vanilla-JS PWA без сборки) — **рекомендую** | один стиль с остальным Betaline; нет сборки; мало памяти (VPS 3,8 ГБ, диск занят на 81%); портируем только нужные ~1,5 тыс. строк логики | UI инбокса и канбана пишем заново (образец — узбекский) |
| B. Форк pcmarket (Next.js) и вырезать лишнее | готовый UI инбокса, тесты | тянем 8,6 тыс. строк lib + чистка; Next-сборка и рантайм на тесном VPS; второй стек в проекте; CRM-часть всё равно писать |
| C. Оживить Nuxt+Supabase-CRM | канбан и карточка уже нарисованы | Supabase — внешний сервис, Vercel блокируется в РФ, переписок нет вообще, auth завязан на Supabase |

### 4.2. Схема

```
посетитель сайта ──► api/chat-ai.js ─┐
формы сайтов ──────► api/lead.js ────┤  POST /internal/ingest  (localhost, общий секрет)
@BetalineAI_bot ───► bot.py (хук) ───┤
(фаза 2) info@ ────► IMAP-поллер ────┘
                                     ▼
                     betaline-admin (Node, :8793, systemd)
                     Postgres БД betaline_admin (локальный, уже стоит)
                                     ▲
           admin.betaline-ai.ru (nginx + LE)  ◄── PWA оператора (телефон/ноут)
                                     │
   ответ оператора ──► сайт-чат: виджет опрашивает GET /api/chat-messages
                   └─► Telegram: sendMessage токеном @BetalineAI_bot через outbox
```

Telegram-карточки в группе **оставляем как есть** — это канал уведомлений; в карточку добавляем ссылку на лид в админке.

### 4.3. Данные (минимум)

- `contacts` — человек: имя, телефон, email, tg_user_id/username, visitor_id сайта, заметка.
- `conversations` — канал (`site_chat`/`telegram`/`form`/`email`), внешний id, статус `ai/needs_operator/operator/closed`, `ai_paused`, `assigned_operator`, `last_message_at`, непрочитанное.
- `messages` — `sender_type user/ai/operator/system`, текст, `meta jsonb`, `delivered_at`.
- `leads` — сделка: contact, `stage_id`, источник (`audit/callback/chat/bot/...`), тариф (`plan`), UTM, сайт (custom/custom2/apex/main), сумма (необяз.), даты.
- `stages` — Новый → Связались → Аудит назначен → КП отправлено → Переговоры → Выиграно / Проиграно (правится в настройках).
- `events` — лента по лиду: создан, смена стадии, ответ, заметка (кто/когда).
- `operators` — логин, хэш пароля (scrypt), имя, роль (`owner/operator`; в MVP роль проверяется хотя бы для настроек и удаления).
- `telegram_outbox` — очередь доставки (из узбекского).

Лид создаётся автоматически: из формы — сразу; из чата/бота — при первом сообщении (стадия «Новый»). Дедупликация в три уровня (уточнение Codex): **повтор события** (уникальный `event_id` от источника → ретрай не плодит дубли), **тот же контакт** (телефон/email/tg_user_id; visitor_id ненадёжен — меняется после очистки браузера), **новая сделка того же контакта** (вторая заявка = новый лид у того же контакта, если прошлый закрыт).

### 4.4. Безопасность и надёжность (обязательно в MVP)

- **Ingest:** только 127.0.0.1 + отдельный секрет на каждый источник (сайт/бот/почта), белый список типов событий, лимит размера и времени тела, идемпотентность по `event_id`.
- **Опрос ответов сайт-чатом:** не по `visitorId` (он из `Math.random()`), а по непредсказуемому токену диалога, который сервер выдаёт при первом сообщении; отдавать только ответы AI/оператора; rate-limit; `Cache-Control: no-store`.
- **Гонка «AI ответил поверх оператора»:** проверять `ai_paused` до вызова модели **и** атомарно перед сохранением/отправкой ответа (как `WHERE NOT EXISTS … ai_paused` в `lib/engine/index.ts` узбеков).
- **Один владелец входящих Telegram-апдейтов** клиентского бота — `bot.py` (polling оставляем); админка только отправляет тем же токеном. Защита от двойного ответа: из админки и reply'ем в старой группе.
- **`/api/lead`:** успех только если лид записан в БД админки (или в Telegram) — не «любой канал». Это меняет семантику `{ok:true}` → влияет на цель `audit_lead` → глобальная правка.
- **Админ-эндпоинты:** cookie `HttpOnly; Secure; SameSite=Strict` + CSRF-токен, права на сервере, rate-limit входа по реальному IP из nginx, экранирование пользовательского текста в UI.
- **Бэкап:** `pg_dump` ночью + копия **вне base-vps** (диск занят на 81%) + один проверенный тестовый restore.
- **152-ФЗ:** перечень данных, кто имеет доступ, сроки хранения/удаления, проверить текст согласия и политики на сайтах (передача в OpenAI уже есть сейчас).

### 4.5. Экраны PWA

1. **Входящие** — список диалогов всех каналов, «ждут ответа» сверху, фильтр по каналу.
2. **Диалог** — переписка, поле ответа, кнопки «Взять / Вернуть боту / Закрыть», справа (на телефоне — вкладка) карточка: контакт, источник, UTM, стадия, заметка.
3. **Воронка** — канбан по стадиям; на телефоне смена стадии кнопкой/селектом (HTML5 drag на тач не работает — грабли старой Vue-CRM).
4. **Лид** — карточка + лента событий + все диалоги контакта.
5. **Настройки** — операторы, стадии, быстрые ответы.

## 6. Мнение Codex

Ревью: `codex exec -m gpt-6-sol -s read-only` (Codex CLI 0.159.2), 07.10.2026. Codex видел только пути к коду и этот черновик; секреты и данные клиентов не передавались. Прод-факты принял как наблюдения автора — проверял только локальный код. Ревьюер на другой модели (GPT), чем автор (Claude) — ревью независимое.

**Вердикт Codex: «согласен с правками».** Ключевое дословно:

> «Разрыв между Telegram, сайтом и CRM описан верно. Но план переоценивает сохранность лидов, переносимость узбекского решения и точность оценки в 10–14 дней.»

> «В `/api/lead` успешный ответ **не доказывает доставку**: `sendToCRM` без настройки завершается успешно, а итог считается успешным при выполнении любого одного канала. Даже отказ Telegram может дать `{ok:true}`.»

> «Узбекский проект нельзя считать готовым образцом персональной авторизации: общая сессия не содержит оператора, имя может прийти из тела запроса, а обработчик ответа допускает смену назначенного оператора при подписанной самовыбранной identity.»

> «Публичный опрос переписки **нельзя делать по `visitorId`**: он создаётся через `Math.random()` и хранится в `localStorage`; нужен отдельный непредсказуемый токен доступа к конкретному диалогу…»

> «Проверки `ai_paused` *до* вызова модели недостаточно: оператор может взять диалог во время ответа OpenAI. Перед сохранением и отправкой ответа нужен повторный атомарный барьер…»

> «Один ночной `pg_dump` на том же диске с занятостью 81% не является достаточным планом: нужны место, вынос копии, срок хранения и проверенное восстановление.»

> «Выбрал бы **A с небольшим зрелым HTTP-фреймворком**, `pg` и лёгким интерфейсом. […] C быстрее даёт вид канбана, но оставляет главную задачу — двусторонние диалоги — почти с нуля.»

> «Задача 4–7 требуют рабочего инбокса и отправки ответа из задачи 8, поэтому „готово“ по ним до неё проверить нельзя.»

Также указал: `close-stale` при мёртвом JWT падает с 500, а не «читает пустой список»; форма не передаёт UTM/сайт; публичный webhook старой Nuxt-CRM пишет в БД service-ключом без проверки секрета; `server.js` ограничивает число чанков, а не байты/время; нужны CSRF, экранирование, 152-ФЗ, поэтапная выкатка на custom2.

**Где я согласен (и уже внёс в документ):** молчаливая потеря лида и новая семантика `{ok:true}`; токен диалога вместо `visitorId`; двойной барьер `ai_paused`; персональная авторизация вместо узбекской модели; ingest с идемпотентностью; бэкап вне VPS с проверкой восстановления; фреймворк вместо голого `http`; поправка про `close-stale`; UTM в форме; порядок задач (инбокс раньше каналов); оценки подняты с 10–14 до 15–20 дней.

**Где не согласен:**
- Codex предлагает отложить **канбан и PWA**. Не согласен: это две из трёх прямых просьб Сергея (смотреть с телефона, видеть стадии). PWA — это S (манифест + sw.js), канбан на фиксированных стадиях — M. Отложил только настраиваемые стадии, быстрые ответы, уведомления и импорт истории — тут с Codex согласен.
- 152-ФЗ — согласен, что нужно, но это не блокер разработки: ПДн уже сейчас лежат в Telegram и уходят в OpenAI. Вынес в открытые вопросы, а не в задачу разработки.
